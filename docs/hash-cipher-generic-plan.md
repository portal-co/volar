# Hash- and cipher-generic spec + pipeline, and Cirrus binding autogeneration

**Status:** plan (not yet implemented).

## Motivation

The spec and the proving pipeline hardcode one hash (Keccak-f[1600] /
SHAKE128 / SHA3-256) and one cipher family (AES, incl. AES-GCM). Three
consumers want a *different*, lighter primitive, and all three are blocked by
the hardcoding:

1. **Cirrus** — the low-spec-target circuit compiler (RISC-V / Arm Cortex-M /
   embedded symbolic-execution runtimes). It consumes `volar_spec` via git
   pins and drifts out of sync with Volar. Its targets are instances where a
   fully-compiled binary is infeasible, so the hash is run **natively inside
   the symbolic executor** — a CPU-friendly ARX hash (**Blake2s**) or the
   NIST lightweight sponge (**Ascon**) is cheaper than Keccak there. The
   bindings to the Volar spec should be **autogenerated** so Cirrus tracks
   Volar instead of drifting.
2. **Recursive proving** — the verifier run **in-circuit** is dominated by the
   transcript/Merkle hashing. A hash that is cheap *as a boolean/arithmetic
   circuit* (Blake2s, Ascon) directly lowers the recursive-prover cost. Ascon
   additionally gives a cheap **AEAD** (Ascon-128a) usable in place of
   AES-GCM where the AEAD is a *choice* (not a conformance target).
3. **PESAT and other memory accumulators** — the per-memory-operation
   absorption challenges (`volar-pesat-emit`'s `derive_challenges`, and
   `cirrus-volar-vole`'s `iop_accumulator` challenge callback) must be
   Fiat-Shamir-bound, which means hashing **in-circuit per memory op**. That
   is the cost driver for memory-heavy programs, so it wants the cheapest
   in-circuit hash available.

## Design

### D1. A two-level hash/cipher abstraction

The same primitive must exist in **two forms** that are differentially
identical:

- **Native form** — for the off-chain prover/verifier and for Cirrus's
  symbolic executor. Use the RustCrypto traits that the codebase already
  depends on: parameterize `volar-iop`'s transcript/Merkle over
  `digest::Digest` (hash) and keep `cipher::BlockCipherEncrypt` (cipher).
  Backends: `sha3::{Shake128,Sha3_256}` (current), `blake2::Blake2s256`,
  `ascon_hash::AsconHash`/`AsconXof`.
- **Spec (in-circuit) form** — for the compiled circuit. The spec dialect
  (const-generic typenum, bounded `for` loops, `Array`, no `Vec`) needs
  *hand-written* spec-dialect implementations of Blake2s and Ascon alongside
  the existing `keccak.rs`, each differentially validated against the
  corresponding RustCrypto crate.

The spec-side selection mechanism is a **design decision** (D4 below) because
the codegen is const-generic and trait-method monomorphization support is
unverified.

### D2. Spec-dialect Blake2s

A `volar-spec/src/blake2s.rs` mirroring `keccak.rs`'s shape: the compression
function (10 rounds, the ARX `G` mixer over 32-bit words), the
parameter-block initialization, and a `SpecSponge`-compatible absorb/finalize
over the 64-byte block. Additions map to the spec's integer `+`; the four
fixed rotations are shifts/xors. **Differential target:** the `blake2` crate
(`Blake2s256`).

### D3. Spec-dialect Ascon (hash + XOF + AEAD)

A `volar-spec/src/ascon.rs`: the Ascon permutation (bit-sliced 5×64-bit
state, the χ S-box = a handful of AND/XOR/NOT per column, the linear layer =
rotations + xors — *very* cheap in-circuit), then Ascon-Hash / Ascon-Xof
(sponge), then **Ascon-128a AEAD** (init / associated-data absorb / encrypt /
finalize / tag). **Differential targets:** the `ascon-hash` and
`ascon-aead` RustCrypto crates.

### D4. Selection mechanism (decision needed)

How spec functions (transcript, Merkle, the accumulator challenge) pick a
hash. Options, in preference order:

1. **A spec-dialect `SpecHash` trait** (`fn absorb`, `fn squeeze`) with one
   impl per primitive, threaded as a type parameter. *Cleanest, but depends on
   the codegen monomorphizing trait methods — unverified.*
2. **Const-generic discriminant** dispatch (`const HASH: usize` selecting the
   backend at compile time). Works within the proven const-generic path but is
   uglier.
3. **Parallel free-function families** (`keccak_sponge_*`, `blake2s_sponge_*`,
   `ascon_sponge_*`) with the *driver* choosing which to instantiate. No
   language support needed; the selection lives at the codegen entry point.

The gate for D4 is a probe: does `volar-lir-codegen` monomorphize a
trait-method call in the spec dialect? (The M4 gate already showed
const-generic free functions monomorphize.) Pick (1) if it does, else (3).

### D5. Fiat-Shamir-bind the memory accumulator

Replace `volar-pesat-emit`'s placeholder `derive_challenges` (currently
deterministic, **not** transcript-bound — the known E3 caveat) with a real
Fiat-Shamir derivation over the abstract hash: `r0..r3 = Hash(program_digest
‖ access_record ‖ step)`. Because this runs **once per memory op in-circuit**,
it is the cost driver — measure it with each backend (D7). The
`cirrus-volar-vole` `iop_accumulator` challenge callback gets the same
treatment (its doc already demands the caller transcript-bind it).

### D6. Autogenerate the Cirrus bindings

Extend the `volar-spec-dyn` precedent (volar-compiler already emits
`generated.rs` — dynamic/runtime-sized types — from the spec) into a real
generator that emits the **Cirrus-facing bindings**: the `volar_spec::vole`
prove/setup surface, the IOP accumulator hook, and the selected hash/cipher
backend, in a form Cirrus's low-spec runtimes can consume. Concretely:

- A generator binary/xtask in `volar-compiler` (next to the existing
  spec-dyn emission) that walks the spec's public API and emits the Cirrus
  binding crate.
- The hash/cipher backend is a **generation parameter**, so Cirrus gets
  Blake2s/Ascon natively without hand edits.
- **Sync mechanism:** a CI check (or a `#[test]` in the generator) that
  regenerates the bindings and `diff`s against the committed copy, failing on
  drift — this is what removes the "Cirrus is out of sync" failure mode.
  Longer-term this replaces the git-pin dependency.

### D7. Cost model to validate (the "why")

Approximate boolean-circuit cost per permutation/block, to be measured in
H2/H3 (these drive which backend each consumer picks):

| primitive | in-circuit (approx. AND-gate scale) | native | best consumer |
|---|---|---|---|
| Keccak-f1600 | ~38K gates (24 rds × 5-bit χ) | medium | on-chain (native `KECCAK256` extern — already done) |
| Blake2s | ~20–30K gates (additions dominate) | **fast (ARX)** | Cirrus symbolic executor |
| Ascon-Hash | **~2–3K gates** (bit-sliced, 12 rds) | fast | recursive proving, PESAT accumulator |

Expected outcome: **Cirrus** picks Blake2s (native speed in the executor),
**recursive proving + memory accumulators** pick Ascon (in-circuit cost), and
the **on-chain** verifier keeps Keccak (the native opcode). One spec, three
backends, each consumer optimal.

|---|---|---|
| H1 | Abstraction layer + native genericity | spec-level sponge/cipher interface defined; `volar-iop` transcript/Merkle parameterized over `digest::Digest` and still pass with `Shake128`/`Sha3_256` (no behavior change); coupling-point survey committed |

| H5 | Accumulator Fiat-Shamir binding | `derive_challenges` transcript-bound; in-circuit per-op cost measured per backend; honest-chain acceptance + tamper rejection still hold |

after H1; H7 last.

## Risks / open questions

- **D4 is the crux.** If the codegen can't monomorphize spec-dialect trait
  methods, the clean trait design falls back to parallel function families.
  Resolve with the H1 probe before writing H2/H3 against a trait that may not
  compile.
- **Security parameter consistency.** Blake2s gives ~128-bit collision;
  Ascon-Hash gives ~128-bit. Both are fine for the Fiat-Shamir / Merkle uses
  here, but the *combination* with the field-size findings in
  `volar-ir/docs/evm-e2e-pipeline-plan.md` (GF(2^128) → ~88-bit) should be
  re-derived per backend so the hash isn't silently the weakest link.
- **AES stays for conformance.** FAEST and the TLS-session proofs *require*
  AES/AES-GCM specifically; Ascon-AEAD only replaces AES-GCM where the AEAD is
  an internal choice (MPC channels, OT), never a protocol-conformance target.
- **Scope of the Cirrus generator.** Autogenerating *bindings* (the API
  surface) is the milestone; autogenerating the full compiled circuit for
  Cirrus's targets is a larger, separate effort (out of scope here).
- **Differential-test hygiene.** Blake2s/Ascon must be pinned against the
  RustCrypto crates the same way `keccak.rs` is pinned against `sha3`, or the
  in-circuit and native forms can silently diverge (a soundness hole in the
  Fiat-Shamir binding).
