# mxx cutover plan: spec autogeneration, transport proofs, and the voof proof chain

Status: active — Phase 0 (M0, `6817355`), Phase 1 (M1, `lwe` element,
`0e442f9`), and Phase 2 v1 (transport proofs for `lwe`) landed. Phase 3
gated on mxx#175.

Phase 2 as landed: `cargo xtask gen-specs` emits, per element, into
`crates/spec/volar-spec-lean/mxx/<element>/`: `Stage.lean` (mxx's own
relational export of the frozen graph), `Native.lean` (`printer_lean`
exact-Nat mode), and `Transport.lean` (generated refinement proofs). The
verification package `crates/spec/volar-spec-lean/mxx/` (lakefile with a
local-path require on a sibling mxx checkout) builds `lwe.Transport`
**with zero `sorry`s**: `mxx_lwe_sample_refines` proves the native spec
function's output is accepted by mxx's stage relation. Transport v1
recognized shape (everything else lands in a `-- NOT-BRIDGED` inventory):
ring dimension 1, single CRT tower, `mat_add`/`mat_mul` only, mat_mul
inner dimension ≤ 3, single matrix output, deterministic graph. voof-side
package wiring is a follow-up.
Upstream tracking: [MachinaIO/mxx#175 — feat: generate security
statements](https://github.com/MachinaIO/mxx/issues/175)

Landed state: `crates/spec/volar-mxx-interop` (the Volar-interop compiler,
mxx pinned at `11004eeb`), `cargo xtask gen-specs` regenerates
`volar-spec/src/mxx_rt.rs` and `volar-spec/src/mxx_lwe.rs` (freshness-gated
by `check-specs`), and `volar-spec/tests/mxx_lwe_cross.rs` cross-checks the
generated element against the hand-written generic `lwe::LweSample`.

## 0. TL;DR

Move `volar-spec`'s lattice-cryptography elements to be **autogenerated from
[mxx](https://github.com/MachinaIO/mxx)** instead of hand-written Rust, in
three staged moves:

1. **Clearly-equivalent items first** — spec elements whose paper binding and
   semantics already match an mxx-expressible program exactly are regenerated
   from mxx DSL graphs via a new Volar-interop compiler (mxx IR → Volar spec
   IR). No behavioral change; the generator replaces the hand-written source.
2. **Transport proofs, generated alongside** — every autogenerated spec
   element ships with a machine-checked equivalence proof between the spec's
   native-Lean backend output (`printer_lean.rs`) and the mxx-generated Lean
   definitions (`mxx_ir_core::lean`), extending the existing
   `printer_lean_bridge.rs` autogeneration pattern into a third direction.
3. **The rest, once mxx has security proofs** — when mxx#175 lands (Lean
   *security* statements, not just the correctness statements mxx already
   exports), the remainder of the lattice support (`tfhe.rs`, `binfhe/`,
   `tfhe_ginx_oracle.rs`, `lwe.rs`, `tinylabels/ring_lwe.rs`, …) is ported the
   same way, and the ported elements inherit a proof chain down to mxx's
   security theorems via **voof**.

As the driving example, we port **mxx's TFHE implementation**
(`mxx/crates/fhe/src/tfhe.rs`) through this system. The Volar-interop
compiler must be ready *before* mxx#175 lands so porting and autoresearch
can start in parallel the moment it does; if no clearly-equivalent spec item
is available sooner, the TFHE port starts earlier as the pathfinder.

## 1. Current state

### Volar side (this repo)

- `crates/spec/volar-spec/src/` lattice-adjacent modules: `ntt.rs` (shared
  pinned negacyclic NTT over `Z_q[X]/(X^N+1)`), `lwe.rs`, `tfhe.rs` (legacy
  TFHE-shaped toy arithmetic, Unpinned / Very unstable),
  `tfhe_ginx_oracle.rs`, `binfhe/` (incl. `gadget.rs`, `lut.rs`),
  `tinylabels/ring_lwe.rs`.
- `crates/compiler/volar-compiler/src/printer_lean.rs` — native Lean 4
  printer over the spec IR (plain functions, `structure`s, explicit hash
  parameters). v1 covers the garble subset; unsupported constructs fail
  loudly.
- `crates/compiler/volar-compiler/src/printer_lean_bridge.rs` —
  autogenerates the *equivalence layer* (struct transports, closure specs,
  commutation theorems) between the Aeneas extraction and the native Lean
  output, from the same spec IR. Unmatched items land in a visible
  `-- NOT-BRIDGED` block.
- `cargo xtask gen-specs` emits
  `crates/spec/volar-spec-lean/volar_lean_generated.lean` and
  `volar_lean_bridge_generated.lean`, freshness-gated in CI by
  `check-specs`.

### mxx side (external, research code, unaudited)

- `mxx-dsl`: Rust-embedded DSL; a program *records* a graph of primitive ops
  (matrix products, Gaussian samples, gadget decomposition, …) with named
  symbolic parameters bound only at run time.
- `mxx-ir-core::lean`: mechanical extraction of a validated frozen graph
  into ordinary **Lean relations** — one relation per frozen scope over the
  handwritten `MxxIR` / `MxxPrimitives` / `MxxRuntime` Lean packages;
  `lean::protocol::export` writes `Stage_*`, `Ideal`, `Backend`, and a
  linked `Claim.lean` per protocol. Claims state the workflow endpoint
  equals the ideal one; noise bounds are proof obligations; a sampling-tape
  option measures claims under a failure probability. This is **correctness
  today**; *security* statement generation is mxx#175.
- `mxx-fhe`: `tfhe.rs` (~1.5k lines) and `bgv.rs` (~1.8k lines) on the DSL,
  with GPU execution via `mxx-backends`. Also `mxx-khe`, `mxx-we` (has its
  own `lean/` modules), `mxx-func-enc`, `mxx-io`.
- mxx#175 (opened by @gkgoat1) explicitly contemplates "mxx IR compiles to
  Volar spec" as the cutover direction and notes real differences between
  the papers volar implements and what mxx provides — hence the
  clearly-equivalent-first staging.

### voof side (sibling repo, `portal-co/voof`)

- hax (Charon + Aeneas) extraction of pinned volar/volar-ir/cirrus revs,
  generated Lean checked in, CI-regenerated.
- Landed: M1 native round-trip proof for the garble subset
  (`Eval_open_Garble_share`); M2 Aeneas-side specs plus the
  `VolarSpecBridge` package transporting between extracted and native Lean
  (`native_roundtrip_via_bridge`), with the bridge layer itself
  autogenerated by `printer_lean_bridge.rs`.

## 2. Target architecture

```text
                 mxx DSL program (single source of truth)
                     |  validate + freeze
                     v
              mxx FrozenGraph  ===========================
                |           |                             |
   Volar-interop compiler   mxx_ir_core::lean::protocol::export
   (mxx IR -> spec IR,      |                             |
    this repo, Phase 0)     v                             v
        |            mxx Lean relations            mxx Ideal/Claim
        v            (Stage_*, Backend)            (security, post-#175)
   volar-spec element (GENERATED Rust, typed IR — no text weaving)
        |  existing pipeline, unchanged
        +--> Rust spec code (no_std, arrays-only per rule 11)
        +--> printer_lean.rs          -> native Lean functions
        +--> printer_lean_bridge.rs   -> Aeneas <-> native transports
        +--> NEW: mxx transport gen   -> native <-> mxx-relation proofs
                                                     |
        voof: Aeneas extraction of the generated Rust |
        |                                             |
        +-------> proof chain <-----------------------+
   Rust impl ==(Aeneas + bridge)== native Lean ==(mxx transport)==
     mxx relations ==(mxx Claim)== ideal functionality / security statement
```

The end state is a **proof chain from deployed Rust code down to mxx-based
security proofs**, with every link either machine-checked in voof or
generated-and-freshness-gated in CI. No link is a hand-maintained parallel
implementation.

## 3. Phase 0 — the Volar-interop compiler (before mxx#175)

A new crate (working name `crates/spec/volar-mxx-interop`, versioned from
`0.0.1`) that lowers a validated, frozen mxx graph into a `volar-compiler`
`IrModule` suitable for the spec pipeline. Requirements derived from the
core design rules:

- **Typed IR only** (rule 1): construct `IrExpr`/`IrStmt` nodes; never
  pre-rendered strings. If the Rust printer mishandles a needed node, fix
  the printer.
- **No `Vec` in emitted program structure** (rule 11): mxx freezes graphs
  with all shapes weaver-known (matrix dimensions, CRT depth, gadget digit
  counts are `IntExpr`s bound at freeze time), so every emitted container
  is `[T; N]` / `core::array::from_fn` / `hybrid_array::Array`. This is a
  natural fit — mxx's whole model is static-shape graphs.
- **Deterministic, no `rand`** (rule 5): mxx samplers become spec-level
  sampling *functions over explicit tapes/seeds*, matching how
  `ExportOptions::sampling_tape` models them on the Lean side, so the same
  tape model serves both the Rust spec and the Lean relation.
- **no_std** per the crate-constraints table for `volar-spec`.
- **Dependency hygiene**: depending on `mxx-ir-core`/`mxx-dsl` requires a
  git dependency or patch; per global policy, check parent
  `.cargo/config.toml` files first and never check in a `patch`ed checkout
  state that conflicts with a parent config. Whether the crate lives in
  this workspace or in the mxx repo as an extra backend is an open question
  (§7); default is this workspace so `gen-specs` can drive it.

**Milestone M0**: the interop compiler round-trips one trivial mxx program
(e.g. the `rlwe_encrypt` example's arithmetic core) into a spec element
that compiles and runs through the existing real-backend tests
(`print_module` → `rustc`), with compile-and-run evidence recorded per the
agents' guide. The compiler must exist and be CI-covered **before** mxx#175
lands.

## 4. Phase 1 — clearly-equivalent items move first

An item is **clearly equivalent** when all of the following hold:

1. The volar spec element and an mxx-expressible program are bound to the
   *same* paper construction and parameterization (no paper drift — the
   discrepancy class called out in mxx#175).
2. All shapes are static under both treatments (satisfies rule 11 without
   a `runtime-boundary` exception).
3. Semantics match on a deterministic cross-test: the mxx-generated
   replacement passes the element's existing spec tests **unchanged**,
   plus new cross-tests against mxx's own CPU executor on shared vectors.
4. The mxx Lean export of the program covers every operation the element
   uses (no missing primitive relations).

Candidate order (assessed against the criteria; re-verify at execution
time):

| Spec element | Why first / why not |
| --- | --- |
| `lwe.rs` (`LweSample::sample`, `b = A·s + e`) | Exactly mxx's matrix-algebra abstraction; landed first as `mxx_lwe` (M1). The hand-written generic stays for now: mxx programs are concrete (all shapes baked at freeze), so the type-generic wrapper cannot be expressed — retirement of the generic form is a later human API decision. |
| `tinylabels/ring_lwe.rs` | RLWE encrypt/decrypt is literally mxx's flagship example shape; next candidate, but needs sampler support in the lowerer (tape-based, see §7). |
| `binfhe/gadget.rs` (gadget decomposition) | mxx gadget nodes are first-class with declared layouts (`BackendLayout`); decomposition semantics must be checked digit-for-digit. Also note mxx rings are prime CRT towers, while binfhe works over power-of-two tori — check for paper drift first. |
| `ntt.rs` (shared negacyclic NTT + pinned params) | **Not a cutover candidate in this form** (corrected after Phase 0): the NTT is a backend *implementation strategy* below mxx's graph abstraction — mxx expresses the ring multiplication itself, not the transform. What could move is code that *uses* `ntt.rs` to multiply, which becomes mxx ring multiplication (executed with NTT on mxx's backends). |
| `tfhe.rs` (legacy toy) | Superseded by the Phase-3 mxx TFHE port; do not invest here beyond what the port needs. |
| `tfhe_ginx_oracle.rs`, `binfhe/` LUT/bootstrap paths | Defer to Phase 3 — these are exactly where paper drift and security-statement needs concentrate. |

Each moved element lands as generated source with a `@generated`
banner (naming the mxx program and rev), regenerated by `cargo xtask
gen-specs` and freshness-gated like the existing Lean/TS outputs.
Generated files change only through the generator pipeline.

**Phase-1 backend scoping (as landed):** generated elements and the shared
`mxx_rt` helpers carry `//! @volar-codegen-exclude:` — they are Rust-only
for now, kept out of the parse-based TS/dyn/Lean-via-reparse outputs
because the TS printer's integer-width inference is not validated for the
`u128` intermediate arithmetic the helpers use, and silently wrong-width
TypeScript is worse than none. Lean coverage comes through Phase 2's
dedicated transport (the interop IR feeds `printer_lean` directly);
TS/dyn coverage follows once those backends are validated for this
arithmetic profile.

## 5. Phase 2 — autogenerated transport proofs (alongside Phase 1)

Extend the existing bridge autogeneration to the mxx direction, generated
in the **same** `gen-specs` run as the spec autogeneration (they share the
frozen graph as input — the transport proof and the spec element can never
drift apart without CI failing):

- **New generator output**: for each autogenerated element, emit a Lean
  module stating that the native-Lean function (from `printer_lean.rs`)
  *refines the mxx relation* for the same frozen scope — i.e. for all
  inputs in the relation's domain, the mxx relation holds of
  `(inputs, native_fn(inputs))`, including the sampler/tape correspondence
  for sampling nodes. Follow `printer_lean_bridge.rs`'s discipline:
  complete proofs for recognized node patterns (matrix mul/add, gadget
  decompose/recompose, NTT butterflies, tape-keyed samplers), and a visible
  `sorry`-free `-- NOT-BRIDGED` inventory for anything unmatched so
  coverage gaps are loud, never silent.
- **voof side**: a new curated package (working name
  `generated/volar-spec-mxx-bridge/`) requiring `VolarSpecNative` and the
  pinned mxx Lean packages (`MxxIR`, `MxxPrimitives`, `MxxRuntime`, plus
  the exported `Stage_*` modules), with the mxx repo added to voof's
  `sources.toml` pins. voof CI regenerates and diffs, same as the existing
  scenarios.
- Noise bounds and other mxx proof obligations remain **obligations**; the
  transport layer only wires the functional refinement. Closing the
  obligations is Phase 3+ work (or mxx's own, post-#175).

## 6. Phase 3 — TFHE port and full lattice cutover (triggered by mxx#175)

- **Trigger**: mxx#175 (Lean security statement generation) landing. At
  that point porting and autoresearch run **in parallel**: the interop
  compiler (Phase 0) is already done, so each mxx security statement
  immediately unlocks the corresponding port.
- **Driving example**: port `mxx/crates/fhe/src/tfhe.rs` (+ `tfhe_gpu.rs`
  scheduling concerns stay mxx-side; the port covers the *protocol*, not
  the GPU planner) into volar as the first large generated element:
  `RingCiphertext`/ring-GSW structure, gadget decomposition, blind
  rotation, key switching — expressed as mxx DSL, compiled to a spec
  element, woven like any other FHE scheme in `volar`. This becomes the
  replacement for the legacy toy `tfhe.rs` and the reference consumer for
  `docs/fhe/` plans; record deferrals in
  `docs/fhe/future-provider-integration-ledger.md` as usual.
- **If nothing is clearly equivalent yet** when TFHE work wants to start,
  start the TFHE port anyway as the pathfinder (it forces the interop
  compiler, the transport generator, and the voof package to exist end to
  end), and let Phase-1 items ride the infrastructure afterward.
- **Rest of lattice support**: with security statements available, move
  `tfhe_ginx_oracle.rs`, the BinFHE paths, and remaining LWE/RLWE support
  through the same pipeline, retiring the hand-written originals.
- **Pinnedness consequences** (human decisions per `reliability.md`): a
  ported element whose chain (Aeneas extraction ↔ native Lean ↔ mxx
  relation ↔ mxx security theorem) is fully closed has the *evidence
  shape* required for **Proven** — proof artifact, theorem name, mxx
  revision, and the voof refinement link. Promotion itself remains a
  maintainer decision per element; this plan only builds the evidence
  path. Until then everything generated stays Unpinned / Very unstable.

## 7. Open questions

- **Crate placement**: `volar-mxx-interop` in this workspace (default; lets
  `xtask gen-specs` own regeneration) vs. an mxx-side backend crate.
  Resolves with the first mxx dependency pin; check parent
  `.cargo/config.toml` before any `[patch]`.
- **Symbolic-parameter gap**: mxx graphs carry symbolic `IntExpr`s bound at
  freeze time; volar spec functions are generic over const lengths. The
  interop compiler must decide, per element, whether to bake bound values
  or map surviving parameters to const generics. Default: bake at freeze
  time (keeps rule-11 compliance trivial), revisit if codegen size hurts.
- **Sampler determinism surface**: exactly how mxx Gaussian/uniform
  samplers map onto `SpecRng` tapes without violating rule 5 needs one
  worked example (the NTT/gadget items avoid samplers; `lwe.rs` forces the
  answer).
- **mxx churn**: mxx is unaudited research code under active development.
  Pin by rev in voof's `sources.toml` and in the interop crate; treat
  upstream API movement as expected maintenance, not surprise.
- **Scope guard**: this plan covers *lattice cryptography*. VOLE, garbled
  circuits, and MPC spec elements stay hand-written; nothing here changes
  the ZK/non-ZK discipline boundary (rule 14) — mxx-sourced FHE material is
  `Transparent` like all FHE modules.
